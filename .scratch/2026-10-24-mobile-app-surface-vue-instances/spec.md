# 移动端应用运行面：每应用一个 Vue 实例（Level 1）— 实施规格

> 状态：**已审核（2026-10-24，结论：值得开发；前置 = 先收口 2026-10-23 保活规格遗留的 Android 手工验收，见 §7.3 步骤 0）**。
> 审核核实记录（2026-10-24）：现状描述、桌面先例（`appSurfaceRegistry`）、`__WASMNEST_SHARED__` 单一 Vue 运行时、Teleport 结构锁位置、ADR 0058 均与代码对上；`app-run-scope` 显式传 pinia 的契约支撑独立 Vue 应用内的 `useStore()`。
> 关系：承接 `.scratch/2026-10-23-app-surface-keepalive/spec.md` 的表面保活口径（首次打开创建、切走保留、停用 / 卸载才销毁），把「移动端运行面应该有几个 Vue 应用实例」这件事固化成可实施、可验收的规格。
> 安全边界引用 ADR 0058：**前端同 webview / 同 JS 信任域；Vue 多实例不是安全隔离。**
>
> 一句话：**壳仍是 1 个 Vue 应用；每个「已打开且有运行面」的应用各建 1 个独立 Vue 应用；每个应用 / 服务仍只有 1 个 WASM 运行期；无界面服务 0 个 Vue 应用。**
>
> **实施注记（2026-10-24 code-review 收口）**：`useAppSurfaces` 实际收窄为只记 `opened`——§4.2 的「当前运行屏插槽」「当前前台应用」随注册表承载退出（容器位置由 `ShellAppSurface` 直接交给 `registry.attach`，前后台信号由注册表按 attach / detach 推动该应用的 `active` ref，见 §4.4）；§4.5 注入清单里的 `wasmnestHostComponents` 已按 issue #24 整面退役，不再注入，其余宿主环境键不变。新增行为锁：创建在途切走不得 attach（C-S8）、销毁抛错不打断停用（C-A15）、T15 / T23。

## 1. Problem Statement

移动端用户已经可以在多个应用之间切换，并且切回来时界面状态还在；但当前所有应用的运行面都挂在**宿主壳的同一个 Vue 应用**里。界面被保活了，应用级上下文却没有分开：

- 所有运行面共享壳的组件树、`app.config`、全局 `provide`、错误处理和清理边界；一个应用里的未捕获 Vue 错误会落到壳的全局错误路径上，壳和其他应用都可能被牵连。
- 应用开发者无法把「这个运行面的根」当成一个独立 Vue 应用来推理：生命周期、依赖注入、错误处理、卸载清理都混在壳里。
- 移动端与桌面端的模型不一致：桌面每个应用运行面已经是独立 Vue 应用 + 容器注册表；移动端仍是「壳内组件 + Teleport 保活池」。
- 服务型应用和无界面服务容易被误建 UI 实例：没有界面的服务不应该因为「应用在运行」就拥有一个 Vue 应用。
- 如果文档或代码把「多 Vue 实例」说成隔离边界，会误导安全判断。它解决的是应用上下文与工程边界，不是 CSS / DOM / 全局 JS / IPC 的隔离。

用户要的结果不是「再多包一层组件」，而是明确的实例模型：**壳一个、每个打开的界面一个、每个应用运行期一个、无界面服务零个**。

## 2. Solution

移动端宿主在 Level 1 采用与桌面同口径的「每应用运行面一个独立 Vue 应用」模型，但保留移动端现有的应用注册契约与共享运行时：

| 对象 | 目标实例数 | 说明 |
| --- | --- | --- |
| 宿主壳 | **1 个 Vue 应用** | 主屏、应用管理、设置、权限、多任务等平台界面仍住在壳里 |
| 已打开且有运行面的应用 | **每应用 1 个 Vue 应用** | 由宿主创建、持有、挂载到该应用自己的容器 |
| 已运行但从未打开过的应用 | 0 个 Vue 应用 | 没有界面可保活，不提前建 UI |
| 已打开但尚未注册运行面的应用 | 0 个 Vue 应用 | 先显示加载 / 空态；运行面出现后再建 |
| 无界面服务（L1 / L2 服务型应用） | **0 个 Vue 应用** | 服务运行期只存在于 WASM 侧 |
| 每个应用 / 服务的 WASM 运行期 | **1 个** | 与 Vue 实例数量解耦；Vue 不决定 WASM 生命周期 |
| 已停用 / 已卸载的应用 | 0 个 Vue 应用 | 唯一销毁点，实例与 DOM 一起回收 |

生命周期仍是既有口径：

```text
首次打开（应用已运行 + 运行面已注册）
  → ensure：创建该应用的独立 Vue 应用并 mount 到自己的容器
  → attach：把容器放进运行屏插槽

切走 / 回主屏
  → detach：容器脱离文档；Vue 应用、组件树、DOM、滚动、表单、内存路由保留
  → 不 unmount、不 dispose

切回
  → attach：同一个容器放回插槽；不重新 createApp、不重新 mount

停用 / 卸载 / 进入错误终态
  → dispose：unmount + 移除容器 + 清掉打开记录；下次启动是全新实例

壳自身卸载（不是应用停用）
  → 只 detach 全部容器，不 dispose；壳重挂后按「打开过 ∩ 运行中」重新 attach
```

Level 1 的共享面保持不变：**Vue 运行时、Pinia 运行期作用域、vue-i18n、router 的既有共享 / 作用域语义保持不变**。不要求应用改入口、改 SDK、改 `registerSurface` 契约，也不新增 WIT / ABI / 权限位。

## 3. User Stories

1. 作为移动端用户，我希望打开一个应用时立刻看到它自己的界面，以便不用关心宿主内部是一个还是多个 Vue 应用。
2. 作为移动端用户，我希望从一个应用切到另一个应用再切回来时，输入框内容、滚动位置、列表状态和页面停留位置都还在，以便操作不会被打断。
3. 作为移动端用户，我希望切到后台的应用继续运行它的 JS 定时器和业务逻辑，以便轮询、连接和任务不中断。
4. 作为移动端用户，我希望后台应用不要继续抢渲染资源，以便前台应用保持流畅、耗电可控。
5. 作为移动端用户，我希望停用应用后它的界面实例真正消失，以便内存和后台任务被回收。
6. 作为移动端用户，我希望卸载应用后它的界面、组件状态和注册面都不残留，以便重新安装时是干净状态。
7. 作为移动端用户，我希望快速连续点击打开、切换、返回时不会出现两个重复的应用界面，以便不会看到重影或状态错乱。
8. 作为移动端用户，我希望一个应用内部报错时壳和其他应用仍然可用，以便单个应用的问题不会让整个桌面崩掉。
9. 作为移动端用户，我希望无界面的服务型应用不要出现在多任务里，也不要因为启动而闪出一个空界面，以便它安静地在后台工作。
10. 作为移动端用户，我希望从服务区打开一个有界面的服务型应用时，它和普通应用一样保留状态，以便服务型应用也能被正常使用。
11. 作为移动端用户，我希望回到主屏再回来时界面不重新加载、不闪加载页，以便保活是用户可感知的。
12. 作为移动端用户，我希望切换语言后所有已打开应用的界面一起更新，以便不需要逐个重开应用。
13. 作为移动端用户，我希望切换主题 / 字体后所有应用界面仍然正确，以便平台设置对应用一致生效。
14. 作为移动端用户，我希望应用在后台被停用时立即销毁界面，即使我没有回到它的运行屏，以便停用是真正的资源回收。
15. 作为移动端用户，我希望 WebView 重载后首次打开一个仍在运行的应用时能重新建出界面，以便后端存活不会变成「有运行期但没界面」。
16. 作为应用开发者，我希望继续用现有的 `registerSurface` 注册一个 Vue 组件，以便不需要为宿主的多实例改造重写应用入口。
17. 作为应用开发者，我希望我的运行面拥有自己的 Vue 应用上下文，以便 `app.config`、错误处理、依赖注入和卸载清理只作用于这个应用。
18. 作为应用开发者，我希望 `inject('pluginContext')` 仍然可用，以便现有取命令、存储、i18n 的代码零改写。
19. 作为应用开发者，我希望 `useI18n()` 仍然可用，以便现有组件的文案不需要改成宿主 context 调用。
20. 作为应用开发者，我希望 `useStore()` / `defineStore()` 的运行期作用域语义不变，以便停用应用时 store 仍被正确作废。
21. 作为应用开发者，我希望 `useRouter()` 仍然解析到宿主共享 router，以便应用内导航和既有插件路由继续工作。
22. 作为应用开发者，我希望宿主注入的平台信息、安全区、键盘信息和宿主公共组件仍可 `inject`，以便现有组件不需要改依赖来源。
23. 作为应用开发者，我希望 `inject(SURFACE_ACTIVE_KEY)` 仍是响应式前后台信号，以便我在后台暂停轮询 / 动画。
24. 作为应用开发者，我希望我的应用不会被宿主隐式塞进另一个应用的组件树，以便组件边界和调试边界清晰。
25. 作为应用开发者，我希望应用级错误不会冒泡到壳的全局错误处理，以便我能从日志里看到是哪个应用、哪个阶段出错。
26. 作为应用开发者，我希望未注册运行面的应用不要被强行创建一个空 Vue 应用，以便无界面服务保持零 UI 成本。
27. 作为应用开发者，我希望运行面组件在注册较晚时也能被正确创建，以便异步加载模块不会导致永久空态。
28. 作为应用开发者，我希望同一个应用连续打开只创建一个 Vue 应用，以便不会出现两个实例争同一份上下文。
29. 作为应用开发者，我希望运行面组件身份变化时旧实例被销毁、新实例被创建，以便不会挂着一个过期的组件。
30. 作为应用开发者，我希望停用应用时先卸载 UI 再拆插件上下文，以便组件卸载期间仍能安全访问 context。
31. 作为平台维护者，我希望移动端实例模型与桌面端一致：壳一个、每个运行面一个、每个 WASM 运行期一个，以便双端可以用同一套术语讨论生命周期。
32. 作为平台维护者，我希望「打开过 ∩ 运行中 ∩ 有运行面」成为创建 UI 实例的唯一判据，以便不会为未打开或已停用的应用建实例。
33. 作为平台维护者，我希望「停用 / 卸载 / 错误终态」成为销毁 UI 实例的唯一判据，以便不会在切换路径上误销毁。
34. 作为平台维护者，我希望壳卸载只 detach、不 dispose，以便壳重挂后还能复用后台实例。
35. 作为平台维护者，我希望壳重挂时能对账并清掉已经不在运行的应用实例，以便不会留下孤儿 Vue 应用。
36. 作为平台维护者，我希望有明确的实例注册表可查询，以便测试和排障能回答「现在到底有几个应用界面实例」。
37. 作为平台维护者，我希望实例创建、attach、detach、dispose 都有带 appId 的日志，以便从日志还原一次切换的生命周期。
38. 作为平台维护者，我希望服务型应用的「不进多任务」逻辑不被这次改造破坏，以便既有产品口径继续成立。
39. 作为平台维护者，我希望 Level 1 不引入每个运行面 Vue 应用自己的 Pinia / i18n / router 安装边界，以便这次改造范围可控、可回滚。
40. 作为平台维护者，我希望 Level 1 不改 WIT、ABI、权限和 manifest，以便不触发跨仓契约重钉。
41. 作为安全评审者，我希望文档明确「Vue 多实例不是安全隔离」，以便不会把组件上下文隔离误当成前端沙箱。
42. 作为安全评审者，我希望文档明确强隔离仍需要 iframe / 独立 webview + postMessage，并按 ADR 0058 留到后续，以便安全边界只有一套说法。
43. 作为 QA，我希望能在不读源码的情况下验证：打开三个应用有三个独立上下文、切走不销毁、停用才销毁，以便验收可重复。
44. 作为 QA，我希望验证无界面服务在启动后实例数为零，以便确认没有偷偷建 UI。
45. 作为 QA，我希望验证一个应用抛错后其他应用仍可交互，以便错误隔离不是纸面承诺。
46. 作为 QA，我希望验证快速切换和并发首次打开不会产生重复实例，以便覆盖最容易泄漏的路径。
47. 作为 QA，我希望验证停用后台应用后组件 `onUnmounted` 被调用、DOM 被移除，以便确认没有内存残留。
48. 作为后续开发者，我希望 Level 2（每应用 Vue 应用级 Pinia / i18n / router 与 SDK getter）可以在这层之上继续演进，而不需要推翻 Level 1 的实例模型，以便架构有延伸空间。

## 4. Implementation Decisions

### 4.1 目标模型与术语

- **壳（shell）**：宿主自身的 Vue 应用，继续只有 1 个。
- **运行面（surface）**：应用注册的根 Vue 组件，代表这个应用在壳内的完整界面。
- **运行面 Vue 实例（surface app instance）**：宿主为某个应用的运行面创建的独立 Vue 应用。它是本规格的核心新增对象。
- **应用运行期（app runtime）**：WASM 侧从激活到停用的生命周期；与运行面 Vue 实例不是一对一绑定。
- **无界面服务（headless service）**：装配角色为 `basic-service` / `internal-business`，且没有注册运行面（或尚未打开）的应用；它只有 WASM 运行期，没有 Vue 实例。

必须区分两个「实例」：

| 说法 | 指什么 | 由谁管理 |
| --- | --- | --- |
| WASM 运行期 | wasm 应用 / 服务的执行实例 | 宿主后端 / 插件管理器 |
| 运行面 Vue 实例 | 应用界面的 Vue 应用 | 移动端宿主前端 |

两个数量可以不同：运行中的无界面服务是「1 个 WASM + 0 个 Vue」；WebView 重载后、用户尚未打开界面时是「可能 1 个 WASM + 0 个 Vue」。

### 4.2 模块职责

- **`useAppSurfaces`（保留，职责收窄）**：继续负责「打开过的应用集合」「当前运行屏插槽」「当前前台应用」三件事；不再负责把运行面组件渲染进壳的组件树。
- **新增运行面实例注册表**：负责 `appId -> { Vue app, 容器, 组件身份, 状态, 前台标记 }` 的创建、查询、attach、detach、dispose；只做 Vue / DOM 记账，不 import Tauri、不认识业务。它是本规格唯一的新测试 seam。
- **`ShellAppSurface`（改造为宿主侧运行面适配器）**：负责解析当前应用的运行面组件、收集宿主环境注入、向注册表 ensure / attach，并渲染加载、空态、挂载失败等宿主状态；**不再**在壳组件树里直接渲染应用运行面组件。它只服务当前运行屏，**不得成为后台应用实例的唯一创建路径**。
- **`ShellHost`（保留生命周期对账）**：负责保证所有「打开过 ∩ 运行中 ∩ 有运行面」的应用都有实例（后台应用也要有），在壳挂载、应用状态变化、运行面注册变化时对账；壳卸载时只 detach，不 dispose。`ensure` 必须幂等，`ShellHost` 与当前运行屏适配器可以都调用它，但同一次打开只能产生一个实例。**销毁对账不能依赖 `ShellHost` 是否挂载**：停用 / 卸载走显式 dispose，错误终态 / 外部停用由模块级应用状态对账或 loader 回调兜底，壳重挂时的对账只是最后一道。
- **`ShellAppRunScreen`（保留插槽与打开登记）**：继续登记 `opened` 和运行屏插槽；不直接拥有应用 Vue 实例。
- **`useShellApps.stop` / `removeApp`（补显式销毁）**：停用 / 卸载时先 dispose 运行面 Vue 实例，再走插件 loader 的 deactivate / uninstall；如果依赖运行态 watcher，仍保留 watcher 作为外部状态变化的兜底。**最易错点（审核标注 2026-10-24）**：现状「停用 → 池内组件卸载」完全由 `ShellHost` 的运行态 watcher 派生（池条目 = opened ∩ running），用户动作路径的销毁必须从「watcher 派生」解耦为显式 dispose——T21 / T24 是这条的护栏，实施与评审优先盯它。
- **`plugin/context.ts` 的 `registerSurface`（原则上不改）**：继续把应用组件包成带 `pluginContext` 的宿主包装组件；独立 Vue 应用可以把这个包装组件作为根，从而保持现有注入路径。
- **`app-run-scope`（Level 1 不改）**：继续负责每个应用运行期的 Pinia store 作用域与停用作废；Level 1 不改成「每个运行面 Vue 应用独立安装 Pinia / SDK getter 返回当前应用实例」。

### 4.3 创建判据

只有同时满足以下条件才创建一个运行面 Vue 实例：

1. 该应用在 `opened` 集合里（用户至少打开过一次运行屏）；
2. 该应用当前处于 `running`（移动端运行态集合只有 `running`）；
3. 能解析到一个运行面组件（`registerSurface` 已注册，或数据源能返回组件）。

任一条件不满足：

- 从未打开 → 不建；
- 已运行但没打开 → 不建；
- 已打开但运行面未注册 → 不建，显示加载 / 预留位 / 空态；
- 已停用 / 卸载 / 错误终态 → 不建，已有实例应被 dispose；
- 服务型且无运行面 → 不建，保持 0 个 Vue 实例。

运行面组件晚到时，注册表应在组件出现后补建一次；不能因为首次解析为 `undefined` 就永久放弃。

### 4.4 注册表接口与不变量

注册表至少提供以下语义（名称可按实现习惯调整，行为不变）：

- `ensure(appId, input)`：确保该应用有且只有一个运行面 Vue 实例；重复调用返回同一个实例；并发调用合并为一次创建。
- `attach(appId, outlet)`：把该实例的容器放进当前运行屏插槽；重复 attach 幂等；未知实例返回失败，由调用方决定是否走首次创建。
- `detach(appId)`：把容器从文档中移除；**不**调用 `unmount`，**不**销毁 Vue 应用；重复 detach 幂等。
- `dispose(appId)`：真正销毁；先摘注册表记账，再 `unmount`，最后移除容器；重复 dispose 幂等。
- `has(appId)` / `list()`：给对账、测试和排障使用；`list()` 只返回当前存活的运行面实例。
- 前台信号：attach / detach 时更新该应用的 active 状态，并推动 `SURFACE_ACTIVE_KEY` 的响应式值。

不变量：

1. 同一 `appId` 至多一个运行面 Vue 实例。
2. `detach` 永远不等于 `dispose`。
3. `dispose` 是唯一会调用 `app.unmount()` 的路径。
4. 注册表先摘记账再 unmount，避免 unmount 期间并发 attach 复用到半销毁实例。
5. 一个实例的容器只属于这个实例；宿主不在容器内部放自己的 DOM。

### 4.5 创建与挂载

- 运行面 Vue 应用由宿主创建，使用**宿主同一份 Vue 运行时**。移动端应用包已经由 SDK 把 `vue` 外置到 `window.__WASMNEST_SHARED__`，Level 1 必须沿用这一点，不能在宿主里再引入第二份 Vue。
- 每个实例拥有自己的容器元素。`app.mount(container)` 会先清空容器，因此宿主的加载 / 失败 / 空态 UI 必须是容器的**兄弟节点**，不能放进容器内部。
- 容器需要给应用根一个确定的高度 / flex 上下文；应用根不应再写 `100vh`。容器默认铺满运行屏插槽的可用高度。
- 创建时安装共享运行时：
  - 共享 Vue 运行时（同一模块引用）；
  - 共享 Pinia 模块与现有 `app-run-scope` 运行期作用域；Level 1 不为运行面 Vue 应用新建 Pinia，也不改变 `defineStore` 显式传入作用域 Pinia 的语义；
  - 共享 vue-i18n 实例（应用消息仍按 appId 前缀合并到宿主 i18n）；
  - 共享 router 实例（Level 1 仍使用宿主 router；插件路由仍在宿主路由表里）。
- 创建时显式注入宿主环境（不能依赖组件树继承）：
  - `pluginContext`（如果注册表能取到；取不到时由包装组件按现有行为处理）；
  - `wasmnestHostComponents`；
  - `platformInfo` / `isLandscape` / `orientation` / `safeArea` / `keyboardInfo` / `safeAreaReady`；
  - `SURFACE_ACTIVE_KEY`（该应用自己的响应式前台信号）。
- 这份环境注入清单是**契约**，不是实现细节：新增 / 删除注入项必须有测试同步，避免应用在独立 Vue 应用里突然 `inject` 到 `undefined`。宿主环境由壳根统一收集一次（或由同一 composable 暴露），`ShellHost` 对账与运行屏适配器共用同一份，禁止两处各维护一份清单。
- `useStore()` 的受支持路径仍是插件模块顶层的 `defineStore`（`app-run-scope` 的既有契约）；窗口外定义的 store 继续走 fail-visible 警告，Level 1 不保证它在独立 Vue 应用里回退到宿主 Pinia。
- 壳应用上注册的全局组件 / 全局指令**不会**自动继承到独立 Vue 应用。应用需要自己 import；宿主公共组件走 `wasmnestHostComponents`，不走全局组件表。
- 如果解析到的运行面组件身份发生变化（例如应用重启后注册了新的组件对象），注册表应 dispose 旧实例并创建新实例，不能继续挂旧组件。

### 4.6 保活、attach 与 detach

- 现有「表面保活」语义不变：首次打开创建、切走保留、停用 / 卸载才销毁。
- 切走路径只允许 `detach`：容器从文档移除，Vue 应用、组件实例、DOM 子树、滚动位置、表单值、内存路由都保留；后台不渲染，但 JS 定时器继续。
- 切回路径只允许 `attach`：同一个容器放回插槽；不重新 `createApp`、不重新 `mount`、不重新执行应用入口、不重建组件树。
- attach / detach 必须幂等；重复调用不能重复 append、不能重复触发前台信号。
- 壳自身卸载（例如进入整页插件路由）只 detach 全部容器，不 dispose；壳重挂后按「打开过 ∩ 运行中 ∩ 有运行面」重新 attach。
- 壳重挂时必须对账：注册表里存在但已经不在「打开过 ∩ 运行中」的实例要 dispose，避免壳卸载期间应用被外部停用而留下孤儿。
- 不做 LRU 淘汰：实例数 = 打开过且仍在运行且仍有运行面的应用数；运行中实例是用户显式状态，不能被宿主静默回收。

### 4.7 销毁

- 唯一销毁判据：应用停用、应用卸载、应用进入错误终态（`ShellAppState.error`）。
- 停用 / 卸载的用户动作路径应**先 dispose UI，再拆插件上下文**：让组件在 `pluginContext` 仍然有效时完成 `onUnmounted` 清理；之后再走 loader 的 deactivate / uninstall。
- 如果是后端状态变化（例如应用自己 `reportError`、外部停用）触发 `ShellAppState.error` / 非 running，销毁对账必须独立于壳是否挂载：由模块级应用状态对账或 loader 回调 dispose，不要求用户先打开运行屏，也不要求 `ShellHost` 还在组件树上；壳重挂时的对账只是最后一道兜底。
- dispose 必须幂等，并且能安全处理「创建还在途」：
  - dispose 开始时先摘注册表；
  - 在途 ensure 完成后发现记账已不在，不得把实例重新登记；
  - 如果实例已经创建但尚未登记，要 unmount 并移除容器。
- `unmount()` 抛错不得留下容器或记账；记录日志后仍然完成清理。
- 注册表的 dispose 只负责运行面 Vue 实例；`opened` 集合与前台标记仍由 `useAppSurfaces` / 壳对账负责。停用 / 卸载路径必须在 dispose 的同时调用 `dropSurface`（或在同一次壳对账中清掉），保证下次打开是全新 Vue 应用、全新组件树、全新运行期状态。

### 4.8 错误隔离与失败面

- 每个运行面 Vue 应用设置自己的 `app.config.errorHandler`；日志必须带 `appId` 和阶段（create / mount / render / event / lifecycle）。
- 运行面 Vue 错误不得冒泡到壳的全局错误处理，也不得让壳或其他应用卸载。
- Vue 错误**不自动**映射为 `ShellAppState.error`，也不自动停用后端：UI 错误是 UI 事实，业务终态由应用 / 后端决定。若应用自己调用 `status.reportError`，再按错误终态走 dispose。
- 创建或 mount 失败时：
  - 不保留半挂载实例；
  - 运行屏显示 fail-visible 的失败态（点名应用与失败原因类别，不白屏）；
  - 下次打开 / 重试可以重新创建；
  - 失败不能影响其他已打开应用。
- 只隔离 Vue 管理范围内的错误；应用自己创建的未捕获 Promise rejection、`setTimeout` 回调、原生事件监听不在 Vue errorHandler 覆盖范围内，仍由应用负责清理和捕获。

### 4.9 服务型应用与无界面服务

- 「服务型应用不进多任务」的既有逻辑不变：`basic-service` / `internal-business` 仍按现有过滤规则不出现在多任务卡 / 切换器。
- 服务型身份**不等于**必须有 UI，也不等于不能有 UI：
  - 无运行面 → 0 个 Vue 实例；
  - 有运行面且用户打开 → 1 个 Vue 实例，按普通应用保活；
  - 有运行面但从未打开 → 0 个 Vue 实例。
- 不得为了「统一模型」给无界面服务创建一个空 Vue 应用；这会违背零 UI 成本，也会让实例数统计失真。

### 4.10 隔离语义（说清楚它解决什么、不解决什么）

Vue 多实例解决：

- 应用级 `app.config`（尤其是 `errorHandler` / `warnHandler`）；
- 独立组件树与根实例；
- 独立 `provide` / `inject` 链（宿主环境通过显式注入桥接）；
- 独立的应用级生命周期与卸载清理；
- 应用级 `appContext`、`globalProperties`、插件安装边界；
- 同一应用内组件共享上下文，不同应用之间不共享组件树上下文。

Vue 多实例**不**解决：

- **CSS 隔离**：所有应用仍在同一 document，全局样式、CSS 变量、选择器互相可见；不是 Shadow DOM。
- **DOM 隔离**：应用 A 仍能查询应用 B 的 DOM；不是 iframe / webview。
- **window / 全局 JS 隔离**：共享 `window`、`__WASMNEST_SHARED__`、全局事件与全局变量。
- **主线程隔离**：一个应用的同步死循环仍会卡住壳和其他应用。
- **Tauri IPC 隔离**：仍在同一 webview、同一 Tauri 命令面；权限边界由 Rust 侧负责，不由 Vue 实例负责。
- **内存隔离**：一个应用的泄漏仍可能拖垮整个 webview。
- **安全沙箱**：前端仍是同可信域。强隔离需要 iframe / 独立 webview + `postMessage` 受控消息桥，按 ADR 0058 留到引入不可信第三方应用时再裁决。

文档和代码注释不得把本改造描述成「前端隔离」「安全隔离」「沙箱」。

### 4.11 契约与兼容性

- **不新增 / 不修改 WIT、ABI、权限位、`plugin.json`、release manifest。**
- **运行面 Vue 实例的创建 / 销毁不触发 WASM 激活 / 停用**：WASM 运行期仍由应用运行态驱动；Vue 实例只是界面承载。停用应用时是「先 dispose UI，再由运行态动作停 WASM」，不是 `unmount` 反过来决定后端生命周期。
- **不修改移动端应用入口契约**：应用仍导出 `activate(context)` / `deactivate()`，仍通过 `context.ui.registerSurface({ component })` 注册运行面。
- **不要求应用重新构建**：Level 1 是宿主侧装载方式变化；应用包仍按现有 SDK 构建，Vue 仍外置到共享全局。
- `pluginContext` 注入键、`SURFACE_ACTIVE_KEY` 符号与语义保持不变。
- 桌面的 `AppMountHandle` / `MOUNT_CONTRACT` 不变；桌面已经是一个运行面一个 Vue 应用，本规格不改桌面。
- 如果后续要改「应用入口由宿主创建 Vue 应用」或「每个运行面 Vue 应用独立安装 router / Pinia / i18n，并让 SDK getter 返回当前应用实例」，属于 Level 2 / 破坏性契约变更，另立规格。说明：现有 `app-run-scope` 已经是「每个应用运行期一个 Pinia」，Level 2 的「每应用 Pinia」指运行面 Vue 应用级安装与 SDK 解析边界，不是重复引入运行期 store 作用域。

### 4.12 并发与竞态

必须覆盖以下路径：

- **并发首次打开同一应用**：合并为一次创建；后到者等待同一个 promise，然后 attach。
- **创建过程中切走**：创建完成后按当前前台状态决定 attach 还是留在 detached；不能因为 late resolve 把旧应用盖到新应用上。
- **创建过程中停用**：dispose 优先；创建完成后不得登记半死实例。
- **快速 A → B → A**：A 的实例只创建一次；attach 幂等；B 的实例按同样规则处理。
- **运行屏过渡期新旧插槽共存**：继续保留「只注销自己登记的插槽」的引用比对规则，避免旧屏卸载抹掉新屏插槽。
- **运行面组件晚到**：组件出现后补建；如果期间应用已停用，则不再补建。
- **壳卸载 / 重挂**：壳卸载只 detach；重挂时先对账再 attach，不能把已停用应用的实例放回插槽。

### 4.13 可观测性

- 创建、attach、detach、dispose、创建失败、unmount 失败都记录日志，字段至少包含 `appId` 和当前实例数。
- 日志走现有前端 logger，不新增 tracing 字段、不加业务指标。
- 不把应用内部状态写进宿主日志；只记录生命周期事实与错误类别。

### 4.14 完成定义

满足以下条件才算完成：

1. 新运行面实例注册表 + 壳接线 + 运行屏接线完成；
2. 新增 / 更新的测试全绿；
3. 现有移动端壳测试全绿；
4. Android 真机手工验收通过（见 §5.6）；
5. `docs/frontend.md` / `docs/architecture.md` / `AGENTS.md` 中描述移动端运行面为「壳内组件 / Teleport 池」的文案同步为「每应用独立 Vue 应用 + 容器注册表」；
6. `git diff` 不包含 WIT、权限、manifest、桌面宿主改动；
7. 不要求应用仓重编；如果实施中发现必须改应用，停下重新裁决，不夹带。

## 5. Testing Decisions

### 5.1 什么算好测试

- 只断言**外部可观察行为**：组件是否 mounted / unmounted、DOM 节点是否同一个、注入值是否正确、前台信号是否变化、应用 A 出错后应用 B 是否仍可交互、注册表当前实例数。
- 不断言私有实现细节：不 spy `createApp`、不断言内部 Map 结构、不依赖具体 Teleport 字符串。
- 用 `getCurrentInstance().appContext` 证明「是不是独立 Vue 应用」：不同应用实例的 `appContext` 必须不同；同一应用内父子组件必须共享同一个 `appContext`。这是比 spy 更稳的行为断言。
- 用组件生命周期计数器证明「detach 不销毁、dispose 才销毁」：`onMounted` / `onUnmounted` 次数是最直接的用户可感知事实。
- 用 DOM 节点身份证明「切回来是同一个容器 / 同一棵子树」：`attach` 后容器节点引用不变，内部输入值 / 滚动位置仍在。
- 用注入值证明「宿主环境桥接没有漏」：运行面组件 `inject` 到 `pluginContext`、`SURFACE_ACTIVE_KEY`、平台信息、宿主公共组件。
- 用错误处理行为证明隔离：应用 A 的事件 / 渲染错误被 A 的 errorHandler 接住，壳与 B 不受影响。
- 测试不依赖真实 WASM、不依赖 Tauri IPC；应用运行态用壳的假数据源 / 假 app 列表驱动。

### 5.2 Seam

**主 seam（唯一新增）**：运行面实例注册表。

- 用真实 Vue + `happy-dom` 测试；注册表接受组件、注入环境、前台信号，返回可查询的实例句柄。
- 覆盖 ensure / attach / detach / dispose / 并发 / 失败 / 组件身份变化。
- 这是最高 seam：它同时覆盖「创建独立 Vue 应用」「容器移动」「生命周期」「注入」「错误隔离」五类行为，不需要为每类行为各开一个模块 seam。

**既有 seam（复用，不新增）**：

- 壳侧接线：`ShellHost` / `ShellAppRunScreen` 现有组件测试，验证「打开登记」「停用出池」「运行屏提供插槽」。
- 应用视图模型：`useShellApps` 的 stop / remove 测试，验证显式 dispose 调用顺序（先 UI 后插件 teardown）。
- 运行面适配器：`ShellAppSurface` 现有空态 / 加载态测试，改为「有运行面时委托注册表；无运行面时零实例 + 空态」。

不为「Vue 多实例」再开第二个新模块 seam；需要验证壳接线时挂在现有壳测试上。

### 5.3 覆盖矩阵

| # | 场景 | 断言（外部行为） |
| --- | --- | --- |
| T1 | 首次 ensure 有运行面 | 组件 `onMounted` 一次；容器里有应用 DOM；注册表 `list()` 含该 appId |
| T2 | 重复 ensure 同一应用 | 仍是同一个 `appContext`；`onMounted` 不增加；不产生第二个容器 |
| T3 | 并发 ensure 同一应用 | 只 mount 一次；两个调用拿到同一实例 |
| T4 | 两个应用 ensure | 两个不同 `appContext`；各自注入到自己的 `pluginContext`；互不覆盖 |
| T5 | attach | 容器进入插槽；DOM 节点引用不变；前台信号变 true |
| T6 | detach | 容器脱离文档；`onUnmounted` 未调用；组件内部状态 / 输入值 / DOM 子树保留；前台信号变 false |
| T7 | detach 后再 attach | 同一个容器节点；同一个 `appContext`；`onMounted` 不增加；状态原样 |
| T8 | dispose | `onUnmounted` 一次；容器移除；注册表不再有该 appId；再次 ensure 得到新 `appContext` |
| T9 | 重复 dispose | 不重复 unmount；不抛 |
| T10 | dispose 期间并发 attach | attach 返回失败；不复用半销毁实例 |
| T11 | 创建过程中 dispose | 最终不登记实例；容器不残留；日志可见 |
| T12 | 运行面组件晚到 | 组件出现后才 mount；出现前注册表为空、显示空态 / 加载态 |
| T13 | 运行面组件身份变化 | 旧实例 `onUnmounted`；新实例 `onMounted`；注册表只保留一个 |
| T14 | 无运行面 / 无界面服务 | 注册表为空；不创建 Vue 应用；不产生容器 |
| T15 | 服务型应用有运行面且打开 | 创建一个实例；服务型过滤逻辑不受影响（既有测试继续绿） |
| T16 | 应用 A 的错误 | A 的 errorHandler 收到带 appId 的日志；壳未卸载；B 仍可交互 / 仍渲染 |
| T17 | 共享 i18n | 运行面内 `useI18n()` 可用；切换共享 locale 后文本更新 |
| T18 | 共享 router | 运行面内 `useRouter()` 解析到宿主 router；导航调用可达 |
| T19 | 宿主环境注入 | 运行面能 inject 到 `pluginContext`、`SURFACE_ACTIVE_KEY`、平台信息、宿主公共组件 |
| T20 | 壳卸载 / 重挂 | 壳卸载只 detach；重挂后同一实例可 attach；已停用实例被对账 dispose |
| T21 | 停用后台应用 | 不需要打开运行屏即可 dispose；`onUnmounted` 被调用 |
| T22 | 卸载应用 | 先 dispose UI 再走插件卸载；不残留注册面 / DOM |
| T23 | 快速切换 A→B→A | 每应用至多一个实例；无重复容器；无旧实例盖新界面 |
| T24 | 壳未挂载时停用 / 报错 | 不依赖 ShellHost 组件树也能 dispose；重挂后不残留实例 |

### 5.5 Prior art

- 桌面 `appSurfaceRegistry` 的 attach / detach / dispose / setActive 测试：本规格的移动端注册表应复用同一组生命周期判据（detach 不销毁、dispose 才销毁、重复 attach 幂等、dispose 期间并发 attach 失败、unmount 抛错也清容器）。
- 移动端 `useAppSurfaces.test.ts`：opened / outlet / active 的既有语义与边角（空 appId、重复登记幂等、只注销自己的插槽）。
- 移动端 `shellAppSurface.test.ts`：加载态 / 空态 / 预留位的用户可感知行为。
- 移动端 `pluginStoreScope.test.ts`：停用应用时运行期 store 作废的既有契约；本规格只保证不破坏它。

### 5.6 手工验收

在 Android 真机（或与真机一致的 dev-shell）上：

1. 打开应用 A，输入内容 / 滚动列表 / 进入应用内二级页；回主屏；打开 B；再回 A：内容、滚动、页面位置原样，且没有加载页闪回。
2. 同时打开 A、B、C 三个应用，在切换器 / 主屏之间来回切：三个界面都保留状态；每应用只有一个可见界面实例。
3. 从应用详情页停用后台的应用 A（不先回到 A 的运行屏）：再打开 A 是全新状态；旧界面的定时器 / 日志不再出现。
4. 停用应用后重新启动：`onUnmounted` 对应的清理发生；再次打开是全新实例。
5. 打开无界面服务型应用（如 monitor 这类服务）：主屏 / 多任务里不出现它的卡；后台只有 WASM 运行期，没有可见 UI 实例。
6. 打开一个有界面的服务型应用：正常显示、切走保活、详情页可停用。
7. 让一个应用在事件 / 渲染中抛错：壳不崩、其他应用仍可交互；日志带 appId。
8. 快速连续点击打开 / 切换 / 返回：不出现重复界面、不出现空白运行面。
9. WebView 重载后打开一个仍在运行的应用：能重新建出界面，不出现永久空态。
10. 切换语言 / 主题：已打开应用的界面跟随更新。

## 6. Out of Scope

- **Level 2：每个运行面 Vue 应用独立的 Pinia / i18n / router 安装边界，以及 SDK getter 返回当前应用实例**。包括运行面级 `app.use(pinia)` / 每应用 locale 覆盖 / 每应用 router 与插件路由重构。Level 1 继续共享宿主 i18n / router，并保留现有 `app-run-scope` 的运行期 store 作用域。
- **CSS 隔离 / Shadow DOM**。应用样式仍在同一 document；不做样式作用域、CSS 变量隔离、选择器封禁。
- **前端强隔离 / 安全沙箱**。不做 iframe、独立 webview、`postMessage` 消息桥；按 ADR 0058，只有引入不可信第三方应用或产品明确要求时才重开裁决。
- **后台持续渲染 / 动画 / 活体缩略图**。detach 后不渲染；应用应通过 `SURFACE_ACTIVE_KEY` 暂停动画 / 轮询。
- **移动端 OS 级保活**（前台服务、开机自启等）。这是另一个票据。
- **一个应用多个运行面 / 多窗口**。本规格仍是一应用一运行面一 Vue 实例。
- **应用入口契约 / SDK 生成物 / `registerSurface` 形状变更**。Level 1 不要求应用重编。
- **WIT / ABI / 权限位 / `plugin.json` / release manifest 变更**。
- **桌面宿主改造**。桌面已经是一个运行面一个 Vue 应用，本规格不改它；只要求术语与生命周期口径对齐。
- **服务型应用不进多任务的逻辑**。该逻辑已实施并有测试，本规格只保证不破坏。
- **LRU / 实例数量上限 / 静默回收**。运行中实例是用户显式状态，不做淘汰。
- **跨应用通信 / 共享状态 API**。应用之间仍通过宿主提供的能力通信，不共享 Vue 实例。
- **应用级 DevTools 面板 / 性能配额 / 内存配额**。
- **焦点恢复**。切回来保留 DOM 与输入值，但不保证浏览器焦点自动回到离开前的元素；需要焦点的应用自行恢复。
- **`Teleport(to: 'body')` 的可见性治理**。运行面自己 teleport 到 `body` 的内容不受容器 detach 影响，这是应用责任；本规格不新增拦截。

## 7. Further Notes

### 7.1 与现有保活规格的关系

- `.scratch/2026-10-23-app-surface-keepalive/spec.md` 定义的是**用户可感知的保活语义**：切走只藏、停用才销毁、后台不渲染。本规格不改变这些语义，只改变承载方式：从「壳内运行面组件 + Teleport 池」变成「每应用独立 Vue 应用 + 容器注册表」。
- 现有保活规格里的「移动 = `useAppSurfaces` 池 + `<Teleport>`」是实现描述，不是不可变契约；本规格实施后应同步更新该描述，避免文档继续指向旧实现。
- 桌面与移动的实例模型在本规格后对齐为：**壳 1 个 Vue 应用；每个运行面 1 个 Vue 应用；每个 WASM 运行期 1 个；无界面服务 0 个 Vue**。桌面应用包自带 Vue 运行时，移动端共享宿主 Vue 运行时，这是双端构建差异，不改变实例模型。

### 7.2 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 独立 Vue 应用拿不到壳的 `provide`，运行面 `inject` 变 `undefined` | 显式环境注入清单 + 契约测试（T19）；新增 / 删除注入项必须同步测试 |
| 共享 router 安装到多个 Vue 应用出现边界问题 | 先用 T18 锁住 `useRouter()` 与宿主 router 身份；若失败，Level 1 可让运行面继续经 SDK `getRouter()` 访问，`useRouter()` 支持降级为 Level 2 项，但不扩大为每应用 router |
| 共享 i18n 安装到多个应用后 locale 不更新 | T17 锁住 `useI18n()` 与 locale 切换；共享实例是同一份，理论上响应式传播 |
| 停用顺序不对，组件在 `pluginContext` 已拆后卸载 | stop / remove 路径显式「先 dispose UI，再 loader.deactivate / uninstall」；ShellHost watcher 只作外部状态兜底 |
| 壳卸载时误 dispose，导致重挂后丢状态 | 壳卸载只 detach；注册表模块级持有实例；重挂对账只 dispose 非运行实例 |
| 壳未挂载期间应用被停用 / 报错，实例残留 | 销毁对账不依赖 `ShellHost`：stop / remove 显式 dispose，错误终态 / 外部停用由模块级状态对账或 loader 回调兜底，壳重挂再对账 |
| 无界面服务被建了空 Vue 应用 | 创建判据强制「有运行面组件」；T14 锁零实例 |
| 并发首次打开 / 停用产生重复实例或半死实例 | 在途 promise 合并 + dispose 先摘记账 + T3 / T10 / T11 / T23 |
| 旧的结构锁逼着保留 Teleport 实现 | 明确删除 Teleport 字符串锁，换成行为断言；锁的是语义，不是模板写法 |
| 改造被误解为安全隔离 | 文档、注释、交付说明统一引用 ADR 0058；只声明应用上下文隔离 |

### 7.3 实施顺序建议

0. **前置收口**：先完成 2026-10-23 表面保活规格（`.scratch/2026-10-23-app-surface-keepalive/`）遗留的 Android 手工验收。本规格 §5.6 与其验收项高度重叠：Teleport 池底座未验收就开始换承载方式，验收期出现的 bug 无法归因（底座还是新注册表）。
1. 先落运行面实例注册表（创建 / attach / detach / dispose / 并发 / 错误处理），用真实 Vue 的单测把 T1–T13 跑绿。
2. 再把 `ShellAppSurface` 改成宿主适配器，接上注入与状态面；跑 `shellAppSurface` 测试。
3. 再改 `ShellHost` / `ShellAppRunScreen` 的接线，跑壳测试；删除 Teleport 结构锁，补行为锁。
4. 再补 `useShellApps.stop` / `removeApp` 的显式 dispose 顺序，跑 stop / remove 测试。
5. 跑移动端全量 `test:run` + `build`。
6. Android 真机跑 §5.6 手工验收。
7. 更新 `docs/frontend.md` / `docs/architecture.md` / `AGENTS.md` 的实现描述；如果团队要求，另开 ADR 记录「移动端运行面每应用一个 Vue 应用」的架构决策。

### 7.4 回滚策略

本改造是宿主侧装载方式变化，应用包不变。若上线前发现阻塞：

- 回滚点 = 恢复「运行面组件直接渲染在壳组件树 + Teleport 保活池」的旧路径；
- 应用无需重编；
- 已创建的注册表模块可以保留但不再接线，或整段回退；
- 不回滚表面保活语义，只回滚承载方式。

### 7.5 待确认项

本规格按已达成结论写成，不再重新讨论以下问题：

- 是否采用「每应用一个 Vue 应用」：是。
- 是否在 Level 1 做每个运行面 Vue 应用独立的 Pinia / i18n / router 安装与 SDK getter：否，Level 2；现有 `app-run-scope` 的运行期 store 作用域不变。
- 是否用 Shadow DOM / iframe / webview 做隔离：否，超出本规格，按 ADR 0058 另裁。
- 是否为无界面服务创建 Vue 应用：否，零个。
- 是否改 WIT / 权限 / manifest：否。

唯一需要在实施前对齐的是**主 seam 是否就放在运行面实例注册表**，以及既有壳测试按 §5.4 调整的幅度；如果团队希望把注册表再拆成「纯记账」与「Vue 创建」两个模块，需要额外说明理由，因为那会增加 seam 数量。
