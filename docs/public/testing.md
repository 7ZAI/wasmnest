# 测试与验证规范（四仓共享）

> **本文件是 `docs/public/`（四仓通用规范）的组成部分**；各仓 AGENTS.md 引用本文件，不复制。
> 与各仓 AGENTS.md 的硬约束同级别。仓特有的测试运行位置 / 工具链 / 完成定义清单见各仓文档（平台仓：`docs/testing.md`；能力仓 / 应用仓：各自 AGENTS.md 的测试节与完成定义节）。

## 1. 单元测试形态

- **按体量选形态，别混用**：① 少量用例 → 同文件末尾 `#[cfg(test)] mod tests`（Rust）或同文件 `*.test.ts`；② 用例多 → 独立测试文件（Rust：`<模块名>/tests/*.rs` 或 crate 根 `tests/*.rs`，**必须确认模块被编译进测试目标**——`mod` 声明链断裂的测试文件静静躺着永不编译）。
- 新增独立测试文件优先按 ② 的目录形态放，不塞进源码主文件。

## 2. 禁止交付

- 无断言 / 恒真断言 / 只测 mock / 快照替代行为断言 / 只为覆盖率的用例——一律禁止。
- 测试要覆盖**行为契约**（正例 / 反例 / 边界 / 异常），不追求数字覆盖率。
- 行为契约覆盖还须包含**副作用**（写库 / 发消息 / 日志 / 外部调用）与**状态迁移**（状态机 / 幂等 / 重试 / 回滚）——只验返回值不验副作用，等于放过一半错法。
- **交付判据以本节与 §4 / §5 为准**。需要系统化产出行为契约时，可借助外部 `unit-test-discipline` skill（行为契约表 → 测试矩阵 → 变异杀死自检）作为**可选工具**；该 skill 的评分卡等自评机制**不构成**本规范的交付门槛（本仓等价且更可执行的机制 = §4 的 Seam 3「锁跑红一次」）。

## 3. 测试数据

- 测试数据一律走临时目录，禁止污染真实数据 / 日志目录；跑完清理或交给测试框架临时目录生命周期。
- 禁止测试访问生产 / 用户真实存储。

## 4. 锁纪律（Seam 3）

- 常规测试之外，各仓存在大量「锁」形式的契约断言（平台仓 `.test.ts` / `*_lock.rs`）。**锁是契约清单，不是障碍**：
  - 合法改动使锁的清单 / 白名单过期 → **同一提交内同步更新清单**并在交付说明点名；
  - 禁止删锁、缩窄 glob、把断言改恒真、吞异常跳过——为「绿」作弊 = 破坏契约防线。
- 迁移 / 新增锁 → 锁必须**跑红一次**证明不空转（至少看到一次真实失败再修绿）。
- 锁读文件失败必须**显性失败**（报错而非静默跳过）。

## 5. 验证底线

- **CI 已恢复（2026-10 起）**：四个仓均有 GitHub Actions workflow（平台 `.github/workflows/test.yml`、能力 / 应用 / 跨端测试仓各自 `ci.yml`）。但 **`dev` 推送不触发 CI**（用户 2026-10-28 定，四仓同口径）——dev 分支的验证仍靠本地命令 + husky + 显式 `workflow_dispatch`，**勿把「CI 会兜底」当依据**。各仓 CI 具体分层与 required checks 见该仓自己的测试文档。
- **任何交付必须实际运行并贴出结果**（命令 + 输出摘要）；无法运行要说明原因与风险。
- 自动钩子（husky 等）跳过（工具缺失等）**不等于门禁通过**——手工补跑对应门禁。
- 迁移期口径：不逐项跑集成 / 全量回归时可只跑**针对性单测 + 所在模块锁**，但对应改动类型的标准验证集（各仓完成定义清单）必须跑通。日常改动至少跑针对性单测与所在端 / 所在 crate 测试。
